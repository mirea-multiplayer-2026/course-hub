Лекция 7. Dedicated Server в Linux (Headless)

Блок 3: инфраструктура, Linux и деплой

Лекция переводит проект из режима локальной разработки в продакшен-подход: отдельный серверный процесс на Linux, автоматический запуск через Application.isBatchMode, сетевые порты, базовая диагностика и архитектура игрового цикла без перезапуска сервера.

1. Зачем эта лекция нужна в курсе

До этого этапа серверная логика проверялась в основном в режиме Host внутри Unity Editor. Такой режим удобен для прототипирования, но не отражает реальные условия продакшена. Лекция 7 переводит проект на инфраструктурный уровень: отдельный серверный процесс, отдельная ОС, отдельная сеть и отдельный жизненный цикл матча.

Что было раньше

Клиент и сервер часто жили в одном процессе. Ошибки инфраструктуры оставались незаметными.

Что делаем сейчас

Поднимаем Linux dedicated server в headless-режиме и подключаем клиент по реальному IP/порту.

Что получаем

Осмысленную архитектуру: сервер управляет матчем, клиенты только реагируют на серверное состояние.

2. Почему Linux стандарт для dedicated server

Выделенный сервер оценивают по трём главным критериям: стоимость владения, плотность размещения процессов и автоматизация эксплуатации.

  • Лицензирование: Linux обычно не требует отдельной лицензии на каждый серверный инстанс.
  • Ресурсная плотность: меньше системных служб и ниже overhead ОС, поэтому на том же железе помещается больше матчей.
  • Автоматизация: инструменты CI/CD, контейнеризация и мониторинг в индустрии в первую очередь ориентированы на Linux.
  • Операционная модель: для игровых серверов привычны headless-процессы, логи в stdout и управление через terminal/SSH.

Практический вывод

Переход на Linux важен не как «мода», а как способ стабилизировать стоимость и масштабирование мультиплеера.

3. Headless-режим: что реально выключается

Headless означает «без пользовательского интерфейса». Для сервера это критично: ему не нужен рендер, камера, звук, меню и локальный input. Ему нужны сеть, физика (если участвует в симуляции), игровой менеджер и синхронизация состояния.

Обычный клиент

Рендер-пайплайн, камера, UI, эффекты, звук, обработка ввода.

Headless сервер

ServerManager, транспорт, матч-логика, таймеры, валидация RPC, игровые состояния.

Результат

Меньше RAM/CPU, быстрее старт, меньше нестабильных клиентских зависимостей в серверном билде.

4. Автостарт через Application.isBatchMode

Главный признак headless-процесса в Unity — Application.isBatchMode. На dedicated server сервер должен стартовать автоматически, без кнопок UI.

using FishNet;
using FishNet.Managing;
using UnityEngine;

public class ServerAutoStart : MonoBehaviour
{
    [SerializeField] private ushort port = 7770;

    private void Start()
    {
        if (Application.isBatchMode)
        {
            Debug.Log($"[Server] Starting on port {port}");
            InstanceFinder.ServerManager.StartConnection(port);
        }
    }
}

Ключевые флаги запуска Linux-билда:

./GameServer.x86_64 -batchmode -nographics
  • -batchmode отключает интерактивный UI-режим.
  • -nographics не поднимает графический стек на машине без GPU.

5. Dedicated Server Build Target в Unity

В Unity 2021+ dedicated build target позволяет физически вырезать часть клиентских подсистем из серверного билда. Это лучше, чем просто запускать обычный клиент «с флагами».

  1. В Unity Hub установить модуль Linux Dedicated Server Build Support.
  2. В Build Settings выбрать Dedicated Server и платформу Linux.
  3. Добавить нужные сцены в билд.
  4. Собрать серверный билд (.x86_64).

Критический нюанс

Серверная загрузочная сцена должна содержать объект с автозапуском сервера. Без этого процесс стартует, но соединение не откроется.

6. WSL 2: запуск Linux-сервера на Windows-машине

WSL 2 для курса удобен тем, что даёт Linux-среду без отдельного физического сервера. При этом сеть у WSL отдельная от Windows-host, поэтому IP нужно брать из WSL.

cd /mnt/e/Builds/GameServer
ls -la
chmod +x ./GameServer.x86_64
./GameServer.x86_64 -batchmode -nographics

Если сервер стартовал корректно, в логах должны быть сообщения о запуске transport и готовности к подключениям.

7. IP и порт: где студенты ошибаются чаще всего

IP-адрес — это «дом», порт — «квартира» приложения в этом доме. Для FishNet/Tugboat в курсе используется UDP-порт 7770.

Для WSL нужен IP именно из Linux, а не из ipconfig на Windows-host:

hostname -I
ss -ulnp | grep 7770

Частая ошибка

Подключение на IP вида 192.168.x.x из Windows вместо IP вида 172.x.x.x из WSL. Клиент не может достучаться до серверного процесса.

8. UDP против TCP в контексте realtime игр

Для геймплея важнее актуальность данных, чем стопроцентная доставка каждого старого пакета. Поэтому realtime-часть обычно идёт через UDP, а важные события дополнительно защищаются протоколом уровня игры.

  • TCP: гарантирует доставку и порядок, но может накапливать задержку из-за ретрансляций.
  • UDP: не гарантирует доставку, но стабильно выигрывает по latency для динамики матча.
  • Практика: позиционные апдейты терпят потерю отдельных пакетов, события старта/финиша матча должны быть гарантированы логикой сервера.

9. Firewall и минимальная сетeвая диагностика

Разрешение UDP-порта в Windows Firewall (PowerShell от администратора):

netsh advfirewall firewall add rule name="GameServer" dir=in action=allow protocol=UDP localport=7770

Минимальный чек Linux-стороны:

# Проверить слушается ли UDP-порт
ss -ulnp | grep 7770

# Проверить что процесс жив
ps aux | grep GameServer

Если процесс есть, но порт не слушается, проблема обычно в коде автозапуска или в неправильной сцене билда.

10. Условная компиляция UNITY_SERVER

UI-код должен быть исключён из серверного билда через UNITY_SERVER:

private void Start()
{
#if !UNITY_SERVER
    startButton.onClick.AddListener(StartServer);
    mainCanvas.SetActive(true);
#endif

#if UNITY_SERVER
    Debug.Log("[Server] Menu skipped in server build.");
#endif
}

Такая развилка держит один репозиторий для клиента и сервера без дублирования сцен и без отдельной кодовой ветки под dedicated build.

11. Deploy-последовательность: от билда до первого подключения

  1. Собрать dedicated Linux build.
  2. Перенести папку билда в путь, доступный WSL.
  3. Выдать исполняемому файлу права через chmod +x.
  4. Запустить сервер с -batchmode -nographics.
  5. Проверить IP через hostname -I.
  6. Открыть порт 7770 UDP во firewall.
  7. Подключить клиент по WSL IP и порту 7770.

12. Игровой цикл как машина состояний

Сервер управляет состоянием матча, клиенты только реагируют на изменения:

public enum MatchState
{
    WaitingForPlayers,
    InProgress,
    ShowingResults
}

public class GameManager : NetworkBehaviour
{
    [SyncVar(OnChange = nameof(OnMatchStateChanged))]
    private MatchState gameState = MatchState.WaitingForPlayers;

    private void OnMatchStateChanged(MatchState prev, MatchState next, bool asServer)
    {
        if (next == MatchState.InProgress)
            ShowMatchUI();
        else if (next == MatchState.ShowingResults)
            ShowResultsUI();
        else if (next == MatchState.WaitingForPlayers)
            ShowLobbyUI();
    }
}

Эта модель защищает от рассинхрона: сервер единственный источник истины, а клиент никогда не «предсказывает» смену глобального состояния матча.

Архитектурное правило

Клиент не решает, когда стартует матч. Решает только сервер; клиенты отображают серверное состояние.

13. Три типовые ошибки в практике

  • Сервер не стартует автоматически: отсутствует или не вызывается код с Application.isBatchMode.
  • Неверный IP у клиента: взят IP Windows вместо WSL.
  • Порт закрыт firewall: UDP 7770 не пропущен, клиент ловит timeout.
Антипаттерн: перезапуск сервера после каждого раунда

Перезапуск процесса ломает сессию и даёт холодный старт. Правильный путь: сервер работает непрерывно, а раунд сбрасывает только игровые переменные и возвращает состояние в лобби.

14. Чек-лист диагностики соединения

  1. Есть ли в WSL лог старта и готовности соединения?
  2. IP взят из hostname -I, а не из ipconfig?
  3. Порт 7770/UDP действительно слушается?
  4. Есть правило firewall для входящего UDP на 7770?
  5. В клиенте введены тот же IP и порт, что на сервере?
  6. В коде есть автозапуск через Application.isBatchMode?
