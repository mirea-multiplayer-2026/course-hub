Лекция 6. Борьба с задержками

Prediction, Rollback и Lag Compensation

Лекция закрывает главный разрыв после миграции на FishNet: почему ввод может ощущаться мгновенным при 200 мс ping, как клиент откатывает собственную симуляцию после серверной коррекции и почему сервер иногда честно засчитывает попадание по цели, которая на экране жертвы уже ушла за угол.

1. Зачем эта лекция нужна

В лекции 5 мы перешли на FishNet и увидели, что у фреймворка есть готовая база под prediction. Но само наличие атрибута [Replicate] не объясняет, почему персонаж двигается сразу, почему иногда происходит коррекция и почему серверу нужна история состояний.

Что было раньше

Мы синхронизировали состояние, RPC и observer-видимость. Управление всё ещё могло ощущаться задержанным при высоком ping.

Что разбираем сейчас

Client-side prediction, input buffer, sequence number, rollback, reconciliation и lag compensation.

К чему идём

К пониманию, как строится отзывчивый, но server-authoritative realtime-геймплей.

Версии, принятые в примерах

Unity 6 LTS, .NET Standard 2.1, FishNet v4.x. Код ниже учебный: он показывает сетевой паттерн, а не готовую production-архитектуру с DI, конфигами и полноценным input-layer.

2. Четыре сетевые проблемы и чем их лечат

Лекция 1 дала диагноз: latency, jitter, packet loss и bandwidth. Лекция 6 показывает инструменты, которые применяются к первым двум проблемам в realtime-играх.

Latency

Чистая задержка пути. Для собственного ввода лечится client-side prediction, для стрельбы по другим игрокам - lag compensation.

Jitter

Нестабильный приход пакетов. Лечится interpolation buffer: клиент показывает немного прошлое, зато плавное состояние.

Packet Loss

Потеря UDP-пакетов. Для input часто применяют redundancy: в каждом пакете дублируют несколько последних вводов.

Bandwidth остаётся важным, но в этой лекции он не главный. Оптимизация payload, квантизация и частота отправки уже разбирались в лекции 2.

Для студентов as-is

Сегодня мы не «ускоряем интернет». Мы строим иллюзию мгновенного отклика: клиент временно показывает ожидаемый результат, а сервер позже подтверждает или исправляет его.

3. Эту проблему решили ещё в 1996-м

Client-side prediction, rollback и lag compensation не являются новой модой FishNet. Эти идеи появились в ранних сетевых шутерах и стали стандартом задолго до Unity.

QuakeWorld, 1996

John Carmack добавил client-side prediction, потому что играть в Quake через dial-up с ping 300 мс без локальной симуляции было невозможно.

Half-Life / Counter-Strike

Valve формализовала latency compensation: сервер проверяет выстрел не по текущему миру, а по миру, который видел стрелок.

Современные игры

CS, Valorant, Apex и другие competitive-игры используют те же принципы. Меняются tickrate, буферы и качество реализации, но не базовая идея.

Методическая заметка для преподавателя

Этот блок нужен, чтобы студенты не воспринимали prediction как «галочку FishNet». FishNet даёт удобный API, но сам паттерн старше большинства современных движков.

4. RTT breakdown: где теряется время

Ping в 80 мс не означает, что игрок видит подтверждённый сервером результат через 80 мс. Реальная задержка ощущения складывается из нескольких участков.

Client input → Server receive → Server send → Client render

RTT = Δ1 + Δ2 + Δ3, где Δ1 - путь input до сервера, Δ2 - обработка на серверном тике, Δ3 - путь snapshot обратно к клиенту. После этого клиент часто добавляет ещё interpolation delay для сглаживания jitter.

  1. Client → Server: ввод летит на сервер примерно half-RTT, например 40 мс.
  2. Server tick: сервер принимает ввод, считает симуляцию и коллизии.
  3. Server → Client: snapshot возвращается ещё примерно 40 мс.
  4. Interpolation delay: клиент держит буфер 100-200 мс, чтобы сгладить jitter.

Итог: при ping 80 мс игрок легко получает около 180 мс задержки между нажатием и подтверждённым отображением состояния. Поэтому клиентские игры не ждут сервер для собственного движения.

Ключевая мысль

У каждого участника сети своё «сейчас». Клиент видит серверное прошлое, сервер получает уже устаревший ввод клиента, а остальные игроки видят ещё более старую интерполированную картинку.

5. Client-Side Prediction одной фразой

Не ждать сервер. Симулировать у себя. Сервер потом подтвердит.

Клиент-владелец на каждом тике читает input, сразу применяет его локально и отправляет на сервер. Сервер позже применяет тот же input у себя и присылает авторитетное состояние.

Что видит игрок

Нажал W - персонаж пошёл сразу. Ощущение такое, будто ping равен нулю.

Что делает клиент

Локально применяет input и сохраняет команду в буфер, чтобы потом можно было переиграть её после correction.

Что делает сервер

Получает input позже, проверяет его и считает авторитетную позицию. Клиентская версия остаётся временной гипотезой.

Учебный код: локальное предсказание без FishNet 
using UnityEngine;

namespace CourseHub.Lecture6
{
    public sealed class LocalPredictionExample : MonoBehaviour
    {
        [SerializeField] private float _speed = 6f;

        private uint _sequence;

        private void FixedUpdate()
        {
            Vector2 input = ReadMoveInput();
            uint sequence = _sequence++;

            ApplyMove(input, Time.fixedDeltaTime);
            SendInputToServer(sequence, input);
        }

        private static Vector2 ReadMoveInput()
        {
            // Учебный пример: в проекте курса ввод лучше читать через New Input System.
            return new Vector2(Input.GetAxisRaw("Horizontal"), Input.GetAxisRaw("Vertical"));
        }

        private void ApplyMove(Vector2 input, float deltaTime)
        {
            Vector3 direction = new Vector3(input.x, 0f, input.y).normalized;
            transform.position += direction * (_speed * deltaTime);
        }

        private void SendInputToServer(uint sequence, Vector2 input)
        {
            // Учебная заглушка сетевой отправки: в FishNet это делает Replicate pipeline.
            Debug.Log($"Input {sequence}: {input}");
        }
    }
}

Сам по себе prediction не отменяет server authority. Клиент не принимает финальное решение, он только временно показывает наиболее вероятный результат собственного ввода.

6. Input Buffer и sequence number

Чтобы потом исправить ошибку предсказания, клиент обязан помнить, какие вводы он уже применил локально. Для этого используется input buffer: последовательность команд с номерами тиков или sequence number.

Input buffer

Локальная история команд: «на тике 142 нажал W», «на тике 143 W+D», «на тике 144 отпустил D».

Sequence number

Номер команды, по которому сервер и клиент понимают, что уже подтверждено, а что ещё ждёт ответа.

Replay

После rollback клиент заново применяет неподтверждённые команды поверх серверной истины.

Учебный код: минимальный input buffer 
using System.Collections.Generic;
using UnityEngine;

namespace CourseHub.Lecture6
{
    public readonly struct MoveCommand
    {
        public MoveCommand(uint sequence, Vector2 input, float deltaTime)
        {
            Sequence = sequence;
            Input = input;
            DeltaTime = deltaTime;
        }

        public uint Sequence { get; }
        public Vector2 Input { get; }
        public float DeltaTime { get; }
    }

    public sealed class InputBuffer
    {
        private readonly Queue<MoveCommand> _commands = new();

        public void Add(MoveCommand command)
        {
            _commands.Enqueue(command);
        }

        public void DropConfirmed(uint serverSequence)
        {
            while (_commands.Count > 0 && _commands.Peek().Sequence <= serverSequence)
            {
                _commands.Dequeue();
            }
        }

        public MoveCommand[] GetPendingCommands()
        {
            return _commands.ToArray();
        }
    }
}

Sequence number решает две задачи: сервер понимает порядок вводов, а клиент понимает, какие локальные команды уже подтверждены и какие нужно переиграть после rollback.

7. FishNet Replicate: что скрывает атрибут

В FishNet prediction-пайплайн упакован в методы [Replicate] и [Reconcile]. Это не магия: под капотом всё равно есть input, tick, буфер, серверная симуляция и коррекция.

[Replicate]

Описывает действие, которое может быть проиграно и на клиенте, и на сервере одинаковым способом.

[Reconcile]

Передаёт клиенту авторитетное состояние сервера, чтобы клиент мог исправить локальную симуляцию.

Цена удобства

API короче, но ответственность остаётся: input должен быть валидируемым, движение - детерминированным, correction - не слишком частой.

Учебный код: FishNet Replicate/Reconcile 
using FishNet.Object;
using FishNet.Object.Prediction;
using FishNet.Transporting;
using UnityEngine;

namespace CourseHub.Lecture6
{
    public struct MoveData : IReplicateData
    {
        public MoveData(float horizontal, float vertical)
        {
            Horizontal = horizontal;
            Vertical = vertical;
            Tick = 0;
        }

        public float Horizontal;
        public float Vertical;
        private uint Tick;

        public uint GetTick()
        {
            return Tick;
        }

        public void SetTick(uint value)
        {
            Tick = value;
        }

        public void Dispose()
        {
        }
    }

    public struct ReconcileData : IReconcileData
    {
        public ReconcileData(Vector3 position, Vector3 velocity)
        {
            Position = position;
            Velocity = velocity;
            Tick = 0;
        }

        public Vector3 Position;
        public Vector3 Velocity;
        private uint Tick;

        public uint GetTick()
        {
            return Tick;
        }

        public void SetTick(uint value)
        {
            Tick = value;
        }

        public void Dispose()
        {
        }
    }

    public sealed class PredictedMover : NetworkBehaviour
    {
        [SerializeField] private CharacterController _controller;
        [SerializeField] private float _speed = 6f;

        private Vector3 _velocity;

        private void Update()
        {
            if (!base.IsOwner) return;

            MoveData data = new MoveData(
                Input.GetAxisRaw("Horizontal"),
                Input.GetAxisRaw("Vertical"));

            Move(data);
        }

        [Replicate]
        private void Move(MoveData data, ReplicateState state = ReplicateState.Invalid, Channel channel = Channel.Unreliable)
        {
            Vector3 direction = new Vector3(data.Horizontal, 0f, data.Vertical).normalized;
            _velocity = direction * _speed;
            _controller.Move(_velocity * (float)base.TimeManager.TickDelta);
        }

        public override void CreateReconcile()
        {
            ReconcileData data = new ReconcileData(transform.position, _velocity);
            ReconcileState(data);
        }

        [Reconcile]
        private void ReconcileState(ReconcileData data, Channel channel = Channel.Unreliable)
        {
            transform.position = data.Position;
            _velocity = data.Velocity;
        }
    }
}

Что важно понимать

[Replicate] не делает клиента главным. Он позволяет клиенту заранее проиграть тот же input, который сервер потом применит авторитетно.

8. Server Reconciliation и rollback

Prediction всегда может ошибиться: серверная коллизия, другой игрок, рассинхрон физики, потерянный input. Reconciliation исправляет это через три шага:

  1. Клиент получает авторитетное состояние сервера на sequence/tick N.
  2. Клиент откатывает локальное состояние к серверной позиции.
  3. Клиент заново проигрывает все неподтверждённые вводы после N.

Не «телепорт», а коррекция гипотезы

Клиентское состояние до подтверждения - это не истина, а прогноз. Если сервер прислал другое состояние, клиент не «проиграл», а получил более точные данные и пересчитал локальную ветку будущего.

Учебный код: rollback + replay 
using UnityEngine;

namespace CourseHub.Lecture6
{
    public sealed class ReconciliationExample
    {
        private const float ErrorThreshold = 0.15f;

        private readonly InputBuffer _inputBuffer = new();
        private Vector3 _predictedPosition;

        public void ApplyServerState(uint confirmedSequence, Vector3 serverPosition)
        {
            float error = Vector3.Distance(_predictedPosition, serverPosition);

            if (error < ErrorThreshold)
            {
                _inputBuffer.DropConfirmed(confirmedSequence);
                return;
            }

            _predictedPosition = serverPosition;
            _inputBuffer.DropConfirmed(confirmedSequence);

            foreach (MoveCommand command in _inputBuffer.GetPendingCommands())
            {
                Replay(command);
            }
        }

        private void Replay(MoveCommand command)
        {
            Vector3 direction = new Vector3(command.Input.x, 0f, command.Input.y).normalized;
            _predictedPosition += direction * (6f * command.DeltaTime);
        }
    }
}

Error threshold нужен обязательно. Без него микроскопические float-расхождения будут вызывать постоянные коррекции и визуальную дрожь.

9. Lag Compensation: честная стрельба в прошлом

Prediction лечит собственное движение. Lag compensation лечит другую проблему: стрелок нажал fire по цели на своём экране, но сервер к моменту получения пакета уже видит цель в другой позиции.

Решение: сервер хранит историю позиций целей, на выстреле откатывает проверку на время выстрела и делает raycast по историческим hitbox.

Почему «убили за углом» не всегда баг

На экране жертвы она уже за укрытием. На экране стрелка в момент выстрела она ещё была видима. Сервер выбирает не текущее «сейчас» жертвы, а момент, когда стрелок реально нажал fire с учётом его задержки.

  1. Сервер хранит историю позиций за последние 0.5-1.0 секунды.
  2. Клиент отправляет команду выстрела с tick/time.
  3. Сервер ограничивает rewind через cap, например 200 мс.
  4. Сервер проверяет попадание в историческом состоянии мира.
  5. Если попадание подтверждено, урон применяется в текущем серверном состоянии.
Учебный код: история позиций для rewind 
using System.Collections.Generic;
using UnityEngine;

namespace CourseHub.Lecture6
{
    public readonly struct PositionSample
    {
        public PositionSample(double time, Vector3 position)
        {
            Time = time;
            Position = position;
        }

        public double Time { get; }
        public Vector3 Position { get; }
    }

    public sealed class LagCompensationHistory
    {
        private const double MaxHistorySeconds = 1.0;
        private const double MaxRewindSeconds = 0.2;

        private readonly Queue<PositionSample> _samples = new();

        public void Record(double serverTime, Vector3 position)
        {
            _samples.Enqueue(new PositionSample(serverTime, position));

            while (_samples.Count > 0 && serverTime - _samples.Peek().Time > MaxHistorySeconds)
            {
                _samples.Dequeue();
            }
        }

        public Vector3 GetRewoundPosition(double serverTime, double requestedRewindSeconds)
        {
            double rewind = Mathf.Min((float)requestedRewindSeconds, (float)MaxRewindSeconds);
            double targetTime = serverTime - rewind;
            PositionSample best = default;

            foreach (PositionSample sample in _samples)
            {
                if (sample.Time <= targetTime)
                {
                    best = sample;
                }
            }

            return best.Position;
        }
    }
}

Почему нужен cap

Без ограничения rewind игрок может искусственно завышать задержку и заставлять сервер проверять попадания в слишком старом мире. Обычно cap держат в районе 200 мс, а точное значение подбирают под жанр.

10. Три участника lag compensation

Стрелок

Видит цель в прошлом серверного времени, но считает свой выстрел визуально честным.

Сервер

Хранит историю и проверяет попадание не в текущей позиции цели, а в позиции на момент выстрела стрелка.

Жертва

Может получить урон уже после ухода за укрытие, потому что на экране стрелка она ещё была видимой.

Это компромисс, а не баг. Если полностью защищать жертву, стрелок будет видеть «попал в голову», но сервер откажет. Если полностью защищать стрелка, жертва чаще получает урон «за стеной». Хорошая netcode-настройка выбирает приемлемый баланс.

12. Топ-7 ошибок

  1. Предсказывать чужой ввод: для удалённых игроков нужна интерполяция, а не фантазия клиента.
  2. Забыть error threshold: микроскопические расхождения превращаются в постоянную дрожь.
  3. Использовать mesh collider как hitbox: lag compensation должен быстро проверять простые формы.
  4. Lag compensation без cap: слишком глубокий rewind открывает чит-вектор.
  5. Синхронизировать позицию через NetworkVariable/SyncVar: для частого движения нужны NetworkTransform, prediction или специализированный поток snapshot.
  6. Tickrate 20 Гц для skill-based shooter: низкая частота сервера не даст ощущение Valorant/CS-like стрельбы.
  7. Игнорировать packet loss: один потерянный input может вызвать рассинхрон и reconcile-коррекцию.

13. Три практических приёма

Hit marker с server confirm

Клиент показывает первичный hit marker мгновенно, а сервер позже подтверждает урон, звук и числа damage.

Разный tickrate

Физику можно считать чаще, чем отправлять snapshot по сети: например, simulation 60 Гц, network send 30 Гц.

Input redundancy

В каждом input-пакете можно дублировать несколько последних команд, чтобы потеря одного UDP-пакета не ломала тик.

Домашнее задание

Расширьте демонстрацию LagGhosts: добавьте четвёртый объект LagCompensatedShooter, который стреляет в moving target и показывает разницу между мгновенным локальным hit marker и серверным подтверждением попадания через rewind.

  1. Стрелок должен показывать локальный hit marker сразу после выстрела.
  2. Сервер должен подтверждать попадание с задержкой, используя историю позиции цели.
  3. Нужно показать эффект «убит за углом» при увеличенной задержке.
  4. Сдача: короткое видео, где виден latency slider и различие локального/серверного решения.

Что мы узнали

  • Prediction работает на клиенте и лечит собственный input.
  • Reconciliation откатывает клиента к серверной правде и переигрывает неподтверждённые вводы.
  • Lag compensation работает на сервере и проверяет попадания в историческом состоянии мира.
  • У каждого инструмента есть цена: CPU, память, риск коррекций, спорные попадания и необходимость cap/threshold.

Связка с лекцией 7

Dedicated server из лекции 7 хранит не только текущую симуляцию. Для качественного netcode ему также нужны input buffers, история позиций, rewind-логика и авторитетная проверка действий клиентов.
